## How to read it

- **Status** is exactly one of:
  - `covered offline`: named offline tests (fakes, models, corpus) assert the whole required result against committed library code, and the row needs no host, guest, hardware, benchmark or release evidence beyond production adoption. It never means the production path or a real host was exercised.
  - `partially covered`: named tests assert part of the required result; the rest, including any host, guest, hardware, benchmark or release evidence the row needs, is open with the named owner.
  - `not covered`: no test at the snapshot asserts any part of it.
  - `needs hardware/host`: the row is only observable on a real host, guest, hardware or authorized environment, and no offline test exercises its own mechanism (tests listed there are related policy coverage only).
  - `not applicable: <reason>`: the plan itself records why no acceptance evidence is required.
- **Evidence** uses the kinds `host`, `guest`, `hardware`, `offline fake/model`, `benchmark` and `release`, joined with ` + `.
- **Existing coverage** lists test functions as `file::test_name` and supporting files or directories as `file`. A path that does not start with `src-tauri/`, `cli/`, `appliance/`, `grid/`, `scripts/`, `docs/` or `e2e/` is relative to `src-tauri/src/`. `via` names the inventory rows whose tests a VM-R requirement relies on. `Gap:` states what the listed tests do not establish.
- **Owner of the rest** names the open assignment in the leftover-task list. E01 owns real VM security/lifecycle runs, E02 the hardware/platform matrix, E03 benchmarks, E04 the numerical checkpoint job, E05 release acceptance; implementation tasks (S, G, M, U, O) own production wiring. O tasks apply only if selected.
- Every applicable row still needs positive, negative, concurrent and recovery cases per supported profile, with explicit unavailable or not-tested reasons (plan §12.2). A model or fake result never certifies the implementation, the host or the hardware (plan §12.3, S2).
- Check the inventory with `python -I scripts/acceptance/check_inventory.py` (optionally `--rev <commit>`). It verifies every referenced file and test function at the revision, that each ID of every range appears exactly once, and that every status, evidence kind and owner is well formed.

## Limits

- Coverage was found by searching HEAD for each ID and by reading test names and doc comments in the modules that cite it; a test that covers a row without a recognisable name or comment can be missing here. Listed tests are representative, not exhaustive.
- The checker proves that each referenced file and test function exists at the revision. It does not run the tests, and it cannot tell whether a test still asserts what its name says.
- Some referenced tests are platform-gated or host-dependent: the VM-CP-15 corpus and the remote_ssh process tests run on Windows only here, symlink cases skip without the privilege, and the corpus test failed once when another session's change met this host's volumes.
- Work in the working tree that is not committed (for example the Firecracker backend files and relay response reader) is not counted. E01Z protocol fuzzing is not at HEAD.
- VM-R status is derived from the cited VM-P rows unless a row-specific reason is given; it shows where evidence would come from, not that the requirement is met.
- GPU-T rows marked covered offline rely on the P16 scenario table's own statement that nothing further is left uncovered offline; production adoption still belongs to the named G and S tasks.
- The combined plan, the leftover-task list and the remaining-only view are untracked in the working tree at this snapshot, so the links above resolve only where those files exist.
