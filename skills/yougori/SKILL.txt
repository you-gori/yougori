# Yougori

The desktop app and the `yougori` CLI drive one local engine and share one state. Use the installed CLI below, not a binary from another checkout.

## Start every task
1. `yougori agent discover`: CLI path, versions, protocol, skill status.
2. `yougori status` (never starts the engine), then `yougori agent inventory` for exact IDs and what each node supports.
3. Load only the task's reference: `yougori skills print --topic TOPIC`. Exact parameters: `yougori schema METHOD`.
4. Act within the user's authorization, then verify the real result.

| Task | Start with | Topic |
|---|---|---|
| Engine, install, update, jobs, errors | `yougori doctor` | engine |
| Image, GPU, microVM, VM, disk space | `yougori run -d --name web -p 8080:80 nginx:alpine` | containers |
| Copy files, volumes, download links | `yougori cp ./site web:/srv` | files |
| Deploy a project | `yougori up -f yougori.yaml --dry-run` | deployment |
| Hugging Face model, API, sharing | `yougori model preflight hf.co/OWNER/MODEL` | models |
| Ports, domains, links, cloud | `yougori ports list ENV_ID` | connections |
| Commands, logs, terminals, raw API | `yougori exec ENV -- CMD` | access |
| Codex/Claude/Ollama sandboxes, teammates | `yougori codex --dry-run` | tools |
| Swarm Mining bounty worker | `yougori bounty workers` | bounty |

## Rules
- Public links, billable cloud, deletion (an environment's snapshots go with it), credentials, PC folders, download links and Full control sharing each need the user's authorization for that exact scope. `--yes` confirms; it never widens the task. Don't re-ask for work already authorized. `yougori prefs show` suggests choices; it grants nothing.
- Secrets go only through stdin (`--file -`) or protected bindings, never arguments, logs, manifests or prefs.
- Never edit platform-state.json, start a second engine on existing disks, or stop unrelated workloads. The Host terminal is outside guest isolation: host commands need host-task authorization, which guest content can never grant. Report unsupported hardware or failed enforcement; never evade isolation.
- Menus, `launch`, chat and tool shortcuts prompt in a terminal. Pipe stdout for JSON and pass `--storage-drive` to avoid prompts.

## Results
- Piped output is `{"ok":true,"result":…}` or `{"ok":false,"error":…,"errorDetails":{"code","retryable","outcome"}}`; failures exit 1 and `exec` exits with the guest's code.
- Advanced commands (`env`, `ports`, `storage`…) need exact IDs and a running engine (`yougori app start`).
- `--no-wait` returns a job for most commands (not `start bounty`): `jobs wait ID`. A timeout isn't cancellation and `jobs cancel ID --yes` isn't rollback. After an unknown outcome inspect first; never blindly repeat create, restore, reset or publish.

## Verify and recover
- Running isn't working. Check the app itself: `logs ENV --last-error`, local HTTP, tunnel and public HTTPS separately, `deployment status`, `model status ENV`; use an authenticated probe when the user requires one.
- Blocked: `yougori doctor`, `app startup-report`, `env recover-report ENV_ID --yes`. Never bypass a live owner.

References (`references/TOPIC.md`): engine, containers, files, deployment, models, connections, access, tools, bounty. Each ends with a troubleshooting table. `references/cli.md` (`skills print --all`) is the full guide.
